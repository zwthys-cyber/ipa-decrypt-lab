# 跨会话任务恢复

机器人仍为 GitHub Actions 限时、管理员私聊测试服务。

## 行为

- 提交任务前，先写入并读回 GitHub Checks 中的恢复记录；记录失败就不提交。
- 新会话会查找最近一天内未完成的记录，接回已有任务，不重复下载。
- 发送文件前记录发送意图。发送成功后记录交付完成。
- 如果进程在发送途中退出，下次启动提示管理员检查聊天，不自动重发。确认未收到后可以明确使用 `/get 任务编号`。
- 已交付任务不会因自动恢复重复发送。手动 `/get` 仍允许重新获取。
- 取消意图先记录；即使取消 API 失败，也停止本会话自动交付。后台工作流可能继续，不能把取消意图当成已停止的证明。
- 恢复任务不自动重做运行器切换，避免重复此前结果不明的备用线路提交。

## 数据与边界

记录仅包含不透明任务编号、App ID、状态、时间及 HMAC。不记录 Telegram 用户数字 ID、聊天消息、更新编号、账号或密钥。签名密钥由机器人 token 与管理员身份派生，其他身份不能恢复该命名空间。更换 token 或管理员会改变命名空间，旧任务需显式编号恢复。

固定锚点提交避免更新代码后丢失索引。最多扫描 500 条记录，达到扫描上限时拒绝继续自动处理；它不是长期数据库。超过一天的记录不自动恢复，与密文短期保留窗口一致，但不保证产物尚未到期。多个未完成任务会停止自动恢复，要求按编号处理。

Checks 的读取可能延迟；读回保护不能提供分布式数据库的一致性或恰好一次交付保证。仍依赖单一会话并发组。Telegram 发送和记录写入无法组成原子事务，发送不确定时优先避免自动重复。

## 验证

`journal-contracts.yml` 在 GitHub 上执行全部 Python 测试，再在两个独立 Linux job 中写入、恢复合成记录，验证身份隔离与已交付状态。它不登录 Apple，不连接 Telegram，不发送真实文件。

本轮结果以该工作流的实际状态为准。多用户服务、收费及全天在线尚未启用。
