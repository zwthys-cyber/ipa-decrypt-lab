# Telegram 使用说明

@ipazake_bot 是管理员私聊入口，服务器端在 Debian 13 VPS 常驻运行。第一版只处理美区免费应用，IPA 最大 2000 MB，暂时没有多用户和收费入口。

## 指令

| 指令 | 行为 |
| --- | --- |
| /start 或 /help | 使用说明 |
| /latest AppID或商店链接 | 下载最新版；单独点击菜单会提示输入应用 |
| /decrypt | 保留为最新版入口的兼容别名 |
| /versions AppID或商店链接 | 查询历史版本并显示可点击、可翻页的按钮 |
| /version AppID或商店链接 版本号 | 实时请求指定旧版，例如 `/version 444934666 9.3.55`；也接受 Apple 历史版本 ID |
| App Store 链接或数字 ID | 默认创建最新版任务 |
| /id | 显示管理员自己的数字 ID |
| /status | 查看当前任务 |
| /cancel | 请求取消当前任务 |
| /get 任务编号 | 显式取回尚未过期的完成文件 |


直接发送链接或数字 ID 就是最新版，不需要额外加指令。菜单会在服务启动时注册。

## 历史版本

提供两种入口：

- `/versions 444934666`：查询历史列表，每页 10 项，点击版本按钮提交下载。
- `/version 444934666 9.3.55`：指定显示版本号；也可以填写已知的 Apple externalVersionID。

两种入口都接受 App Store 链接，不接受 Bundle ID。至少 6 位、非零开头的纯数字按 Apple externalVersionID 处理，它与 Info.plist 的 CFBundleVersion 不是同一个字段。

首次查询最多核对最近 10 个历史标识，完成后立即显示按钮。需要更早版本时，点击“加载更早版本”，每次再核对最多 10 个标识。已经加载的页面可直接翻页，不启动 GitHub；单个应用最多展示 200 个版本。每批在请求之间检查 180 秒预算，连续 3 次元数据查询失败就停止；游标会跳过已尝试的标识，避免反复卡在同一版本。

最多缓存 50 个应用，24 小时内直接使用。超过 24 小时、未满 7 天的列表先显示旧缓存，空闲时后台刷新；忙碌时可以继续浏览，稍后点“刷新列表”。超过 7 天的缓存会删除。缓存和查询状态写入数据库，重启后保留。

首次查询和刷新至少间隔 60 秒，加载更早版本至少间隔 5 秒；这些远程查询合计每滚动 24 小时最多 20 次。点击“刷新列表”会重新查询最近一批。按钮仍在 6 小时后过期；重新发送 `/versions AppID` 可以从缓存打开新按钮。

指定显示版本号时，搜索上限为 120 个标识，同样有时间预算。Apple 不再提供下载、账号没有许可或版本匹配失败时，任务会停止，不退回最新版。旧版请求不拿最新版的商店大小作拒绝依据，实际文件仍受 2000 MB 限制。

按钮绑定管理员、私聊、列表消息和有效期，使用状态先写入数据库，再提交任务。选择版本并通过任务检查后，列表自动收起为“已选择版本”的简短提示，所有版本和翻页按钮移除。收起状态在重启后保留，后台刷新也不会重新展开；需要再次选择时，重新发送 `/versions AppID`。

已实测 QQ 的按需历史目录：Apple 返回 335 个标识，[首批](https://github.com/zwthys-cyber/ipa-decrypt-lab/actions/runs/41952989754)和[下一批](https://github.com/zwthys-cyber/ipa-decrypt-lab/actions/runs/41953354529)各返回 10 项，标识不重叠。Apple 的 releaseDate 在这个样本里是应用首次发布日期，所以没有把它显示成每个版本的发布时间。

## 进度和文件

进度卡显示阶段、任务编号和已用时间，同阶段约 15 秒刷新，也可以发送 `/status`。只有 Telegram 返回文件发送成功的回执后，才显示 100%；上传接口没有可靠的逐字节回调，没有加估算百分比。

交付文件使用 `名称_版本.ipa`，例如 `My BVF_5.2.3.ipa`。名称和版本取自校验后的 IPA，图标优先取包内 PNG，缺失时尝试 Apple 商店图标。商店图标可能对应最新版；取图失败不影响文件发送。文件附件不再附加校验说明和任务编号那三行文字。

如果出现“上次文件发送结果需要确认”，先查看聊天里是否已经收到文件。确认未收到后，再用 `/get 任务编号` 取回。保留这个判断，是因为 Telegram 发送和本地状态写入不能作为同一笔事务完成，超时不一定等于发送失败。

## 任务怎么处理

1. 服务器检查应用的美区上架状态、价格和标注容量。明确不支持时直接返回，不创建任务、不占提交额度。
2. GitHub macOS 获取匹配的预编译运行包，登录账号并请求下载。
3. 复用已有模型处理 IPA，核对所有加密切片、版本和摘要，清理 Store 账号元数据。
4. 用 age 加密结果，公开产物只保留一天。
5. VPS 解开交付密文，复核摘要和 IPA 结构，再通过本地 Bot API 发到管理员私聊。

没有把解密成功等同于安装成功；重签名和实际运行仍需另行验证。

同一时间只运行一个 Apple 下载或查询工作流；旧缓存后台刷新时可以提交下载，由 GitHub 串行执行。普通下载默认每 UTC 日最多 20 次提交（包含失败任务），提交间隔至少 30 秒；历史列表查询单独计数。工作流默认使用 macOS 26 Intel，备用 macOS 15 Intel。只有确认原任务未执行且已终止，才允许安全切换，最多两次逻辑运行。

## 运行包和速度

已把逐任务编译改成约 28 MB 的成品包。代码更新时在 GitHub 构建和测试，普通任务直接下载并验证源码指纹、平台和摘要。

四个固定 Apple 公共资源单独缓存，每次仍校验长度和 SHA-256。缓存只包含公开资源，不包含账号会话、授权模型或 IPA。跨 macOS 运行器的实测中，恢复和校验合计约 6 秒；之前重新准备资源曾用 24–71 秒。

[My BVF 最新回归](https://github.com/zwthys-cyber/ipa-decrypt-lab/actions/runs/41953586939)约 59 秒，包准备 7 秒、公共资源恢复及校验 8 秒。历史查询进一步复用同批连接和公开端点后，[QQ 首批 10 项](https://github.com/zwthys-cyber/ipa-decrypt-lab/actions/runs/41956106639)约 55 秒，[下一批](https://github.com/zwthys-cyber/ipa-decrypt-lab/actions/runs/41956309828)约 1 分 3 秒。下一批与前次耗时接近，并非每次都会明显提速。这里记录的是工作流作业耗时，排队和 Telegram 展示、文件传输另计。

Actions 运行包保留 30 天，每周刷新。源码更新后需要先完成新构建；缺包时运行 `native-runtime-build.yml` 补齐，再提交任务。

## 配置与恢复

将 Apple 账号和模型放在 GitHub Secrets。VPS 只保存 Telegram 凭据、交付私钥和限定仓库权限的 GitHub token。部署配置见 [VPS 说明](VPS-DEPLOYMENT.md)，公开版本见 [发布说明](RELEASES.md)。

恢复记录保存在私有 SQLite。重启后继续跟踪原任务，不重复提交；发送结果不明时不自动重发。不要在另一台机器启动同一个机器人的轮询进程。具体规则见 [任务恢复](SESSION-RECOVERY.md)。
